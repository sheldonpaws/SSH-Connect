# AGENTS.md

Windows-only SSH client for Linux VPS ("Dog Wisdom" project). Desktop app (Python 3.13 + Tkinter) that drives a bundled KiTTY (`kitty.exe`) plus a web interface (FastAPI, auto-launched after connect). UI/log strings are in Russian — keep new user-facing strings in Russian.

## Run

- Use the bundled venv `SSH_env` (gitignored inside itself via `SSH_env/.gitignore`), then:
  - `python main.py` — desktop app with console. `main.pyw` = console-less variant.
  - `start_project.bat` — launcher (also starts the bundled `move_cursor` helper).
- Web interface: normally auto-launched by the GUI after connect; standalone `cd web-desktop/backend; python main.py` → uvicorn (`reload=False`) on `http://127.0.0.1:8000`, frontend served from `web-desktop/frontend`. No build step for the vanilla JS frontend.
- Tests: stdlib `unittest` only (no pytest/httpx in `SSH_env`) under `tests/`, run `SSH_env\Scripts\python.exe run_tests.py` (or `python -m unittest discover -s tests -t . -v`). Offline, no VPS needed; network/VPS paths (SSH connect, hermes port-forward) are exercised with fakes or skipped. No linter/CI. Also keep running `python main.py` as the GUI smoke check.

## Architecture

- `main.py`, `ssh_client.py`, `main.pyw` all route to `src.gui.SSHApp`. `ssh_client.py` is a legacy shim; keep imports pointed at `src/`.
- Main window design (restored from backup `D:\SSH-Connect\src\gui.py`, FANGUNION theme): 980x460, dark DWM titlebar (attrs 20/35, caption 0x20121A), `theme_use('clam')`, Georgia UI font, dark palette (`PAL_BLACK_VELVET #1a1220` bg / `PAL_TEXT #e8dff0` / accent `PAL_GOLD #d4a853` / violet shades). Two `ttk.LabelFrame`s: «Подключение» (profile combobox with placeholder «Новое подключение», host/port/username/password/key fields, buttons «Подключиться», «Отключиться», «Веб-интерфейс», «Docker-браузер», «Доступ» + access_status рядом с кнопкой «Доступ» — индикатор обратного доступа, ● (серый/зелёный), tmux row 5) and «Журнал» (`output_text`, tags `command`/`output`/`error`/`success`/`info`/`warning`, Consolas 11). All dialogs are custom dark dialogs (`_dark_dialog`, `_dlg_info`, `_dlg_error`, `_dlg_confirm` with danger-red kill button, `_dlg_askstring`) — no stock `messagebox`. No emoji icons on buttons (log text may use ⚪/🟢/🌐/🐳 glyphs).
- The interactive terminal is NOT tkinter — it is `kitty.exe` (KiTTY). `KittyController` in `src/gui.py` drives it via Win32: password AND commands are sent with `PostMessage` WM_CHAR (never on the command line; works even minimized — mirrors `kitty_launcher.py` exactly), and a `%TEMP%\kitty_session.log` file is watched to detect the password prompt and auth failures. KiTTY is launched with the `-log` flag (not `-sessionlog`).
- The GUI launches the web interface on demand (button «Веб-интерфейс»): `_open_web_interface()` (`src/gui.py`) starts uvicorn as a hidden subprocess if 127.0.0.1:8000 isn't already up, creates an SSH session via `.server_token` (POST `/api/connect`) and opens the browser tab. Log output for the spawned server goes to `web-desktop/backend/server.log`. If uvicorn/fastapi are missing in the venv it falls back to hard-coded Python312 install paths.
- tmux session management: GUI row 5 of the connection panel acts on the remote server (see "tmux UI" below for current layout). Commands go to the KiTTY window via `_send_to_kitty` (KiTTY must be up); listing runs `tmux ls` via paramiko (`_execute_server_command`). «Удалить» shows a non-reversible warning dialog and detaches from the current session (`tmux detach`) before killing. There is NO «Сохранить» button anymore — `_tmux_save` was removed. All GUI buttons have no emoji icons. Enabled only while connected.
- Feature modules: `src/ssh.py` (paramiko/SFTP), `src/utils.py` (profiles in `ssh_connections.json`), `src/hostkeys.py`, `src/encryption.py`, `src/terminal.py` (older standalone terminal, not used by the main UI), `src/clipboard_sync.py` (clipboard sync with docker browser), `src/reverse_access.py` (reverse tunnel file server). Web interface backend: `web-desktop/backend/{main,ssh_manager,file_manager,kitty_launcher,hermes_manager}.py` (REST files + upload/download + `/api/programs` list of installed utilities + `/api/launch` + Hermes agent chat).
- `move_cursor.py` (project root, single file): PgUp/PgDn → `PostMessage` WM_MOUSEWHEEL/WM_MOUSEHWHEEL to the active KiTTY window, so tmux `mouse on` scrolls its own history. Replaces the old `move_cursor/` package (deleted — single file now). Implemented via a **pure-ctypes Win32 low-level keyboard hook** (`WH_KEYBOARD_LL`) — no pynput dep. The PgUp/PgDn keys are SWALLOWED while a KiTTY/PuTTY window is foreground, so KiTTY/tmux never see the raw key and only the synthetic wheel scrolls (this is why `notches` actually takes effect — the native tmux `PgUp=copy-mode` binding would otherwise page-scroll independently). Settings live in `move_cursor.json` (auto-created at first run, next to the script): `pause_key` (F12), `up_key`/`down_key` (Page Up/Down), `notches` (wheel notches per press, configurable WITHOUT editing code), `notch_delay` (pause between notches so KiTTY doesn't merge rapid wheel posts), `horizontal` (Shift+PgUp/PgDn). Actions + loaded config are logged to `move_cursor.log`. Started/finished by the GUI: `_start_move_cursor`/`_stop_move_cursor` in `src/gui.py`, process tracked in `self._move_cursor_proc`, killed on disconnect and window close.
- Web file transfer (upload/download): `POST /api/files/upload` is ONE file per multipart request (`session_id`, `path` = full remote destination, `file`) — intermediate folders are auto-created via SFTP `_mkdirs` (race-safe), so the frontend uploads folder trees file-by-file with per-file progress (buttons ⬆ files / 📁⬆ folder via `<input webkitdirectory>`; folder name from `webkitRelativePath` is preserved as a subfolder). `GET /api/files/download?path=&session_id=` streams a file binary-chunked via `FileManager.iter_download` (no 1 MB text limit — the old text-only implementation corrupted binaries) or, for directories, streams `tar -czf -` produced ON the server via `iter_tar` (huge dirs never hit API memory). Because the auth token only travels in the X-Auth-Token header, downloads go through fetch→blob→objectURL in app.js — a direct `<a href>` link would get 403. Content-Disposition uses RFC 5987 `filename*=` for Cyrillic/space names. python-multipart (already in SSH_env) is required for the upload endpoint.
- Reverse access (GUI button «Доступ» + indicator `access_status` ⚪/🟢): `src/reverse_access.py` serves the chosen Windows folder(s) over a local `ThreadingHTTPServer` on 127.0.0.1 (GET/PUT/MKCOL/DELETE, path-traversal guarded by `commonpath`) and exposes them on the VPS via a parametrized paramiko **reverse** port forward — `transport.request_port_forward("127.0.0.1", 17850)`. Port is **fixed at 17850** (`ReverseAccess.FIXED_PORT`): if busy on the VPS, start FAILS with a clear error (never a random port — that made the agent's URL flop and "confuse ports"). **Multiple folders are supported on that ONE port** as sub-paths `http://127.0.0.1:17850/<slug>/...`: «Доступ» opens a folder manager (runtime dialog, listbox + buttons «Добавить»/«Убрать»/«Стоп доступ»), and `_start_reverse_access` (re)builds `ReverseAccess` mounts `{slug: folder}` — restart preserves existing slugs (`_reverse_slugs`) so URLs don't change when adding/removing folders; `make_slug` transliterates Cyrillic folder names (`Мои документы` → `moi-dokumenti`). `recover()` MUST NOT be re-added; keepalive (set in `src/ssh.py`) prevents dropouts. URL is stable `http://127.0.0.1:17850/` with per-folder `/slug/` suffixes. `_toggle_reverse()`/`_stop_reverse_access()`/`_manage_reverse_dialog()`/`_sync_reverse_manifest()` in `src/gui.py`; the button is enabled only while connected, and access stops on disconnect/window close. The GUI writes `{folder: url}` entries (full URL incl. `/slug/`) in `~/.hermes/reverse_access.json` on the VPS (`_sync_reverse_manifest` → `_write_reverse_json` via base64 piping — the agent reads its accessible folders/URLs from there; never write into SOUL.md; `_read_reverse_json` drops old-format junk like `records` arrays). The Hermes side knows the mechanism via the `reverse-ssh-tunnel` skill (`~/.hermes/skills/devops/reverse-ssh-tunnel/SKILL.md`, local+enabled on the VPS — its description covers both diagnostics AND mapping Windows paths to `http://127.0.0.1:17850/...` via curl GET/PUT/DELETE/MKCOL; includes a "do NOT touch sshd" guard). The GUI auto-installs the skill on connect: after a successful SSH connect it runs `_ensure_hermes_skill` (background thread) → `src/hermes_skills.py:install_skill_if_missing`, which writes `REVERSE_SSH_TUNNEL_SKILL` into `~/.hermes/skills/devops/reverse-ssh-tunnel/SKILL.md` if missing (base64 via `bash -lc`, quiet skip when hermes absent). Content is NOT hand-maintained: the single source of truth is `skills/reverse-ssh-tunnel.md`, and `skills/gen_hermes_skills.py` regenerates `src/hermes_skills.py` from it (run `python skills/gen_hermes_skills.py [--check]` after editing the skill). This replaced the old manual mirroring. The constant stays PyInstaller-safe (pure string, no file resources). The skill is local+enabled once the file exists in the existing `devops` category (a NEW category is NOT registered — tested). The web chat ticks that skill by DEFAULT (`DEFAULT_SKILLS = ['reverse-ssh-tunnel']` in `web-desktop/frontend/js/hermes.js`) — users don't need to enable anything. `stop()` order matters: `shutdown()` then `server_close()` (`_stop_local_server`, WinError 10038) and `_serve_forever_safe` suppresses tracebacks.
- tmux UI: the tmux row (row 5) is a readonly Combobox (`tmux_session_combo`) + buttons «Подключить»/«Отключиться»/«Новая»/«Удалить». The combobox lists live sessions: clicking it re-runs `tmux ls` (`_on_tmux_combo_click` → `_refresh_tmux_combo`); with no live sessions it shows the placeholder «Нет сессий» (`SSHApp.TMUX_NO_SESSIONS`, guarded out as a no-op in `_tmux_attach`/`_tmux_kill`). «Подключить» and «Удалить» take the selected session from the combobox (no name dialogs). «Подключить» (`_tmux_attach`) sends `tmux switch-client -t <name> 2>/dev/null || tmux attach -t <name> 2>/dev/null || echo 'Нет сессии tmux'` to KiTTY — switch works when already inside a tmux session, attach is the fallback outside, and a vanished session/server prints «Нет сессии tmux» instead of tmux's English "error connecting to …". «Отключиться» (`_tmux_detach`) simply sends `tmux detach` to KiTTY (no session from the combobox needed; works whenever the terminal is inside tmux). «Новая» (`_tmux_new`) schedules `root.after(3000, _refresh_tmux_combo)` because KiTTY typing + tmux startup lag means the fresh session must be re-read late to appear in the list. There is NO «Список» button anymore — `_tmux_list` was removed; NO «Сохранить» button either — `_tmux_save` was removed; `_tmux_sessions()` parses `tmux ls` names. Enabled only while connected.
- Hermes Agent integration (Nous Research agent installed on the VPS at `/usr/local/bin/hermes`): state lives in `~/.hermes` OF EACH SSH USER (root → `/root/.hermes`, sheldon → `/home/sheldon/.hermes`; both installs exist on the test VPS). The binary is NOT on non-login-shell PATH for per-user installs (`~/.local/bin/hermes`) — commands must run via `bash -lc`. sheldon's working default model/provider: `laguna-s-2.1-free` via `opencode-free` (keyless relay at opencode.ai/zen, separate from OpenRouter's 50/day free quota which auxiliary calls like title-generation burn fast; valid free IDs live in `~/.hermes/provider_models_cache.json`). `web-desktop/backend/hermes_manager.py` wraps the hermes CLI over the existing SSH session — each chat message runs `hermes chat -q <msg> -Q [--resume ID] [-s skills] [-m model] [--yolo]` as a background "job" thread reading paramiko stdout incrementally; frontend polls `GET /api/hermes/job/{id}?offset=N`. Endpoints: `/api/hermes/send|job|stop|sessions|skills|home|jobs/list|jobs/read|jobs/delete`. `/api/hermes/home` returns the connected user's `$HOME` + whether `~/.hermes` exists — the web page builds ALL memory-file paths from it dynamically (never hardcode `/root/.hermes`: connecting as a non-root user gets Permission denied). Args are shell-quoted with `shlex.join` per argument (never string-concatenate user text into the command). Rich tables from `hermes sessions list` / `hermes skills list` are parsed by `parse_rich_table` (splits on BOTH `│` and `┃` — rich uses heavy `┃` for header borders, light `│` for data rows). Session id is extracted by `extract_session_id`: first line `session_id: <id>` (format like `20260821_133032_62b770`, NOT a UUID), fallback = last UUID. Every web send creates a `~/.hermes/jobs/hj_<jobid>.log/.q` job file (the same `session_id:` line is written into the log), and `POST /api/hermes/sessions/delete` ALSO removes that session's related job files (grep `session_id: <sid>$` over hj_*.log, rm the .log and .q pair) — otherwise the «Задачи» spoiler accumulates dead jobs forever. Job output is stripped of ANSI color codes statefully in `HermesJob._append` (hermes ignores NO_COLOR in some warnings; incomplete escape sequences at chunk boundaries are held back until the next chunk). Web chat page: `/hermes` → `frontend/hermes.html` + `js/hermes.js` + `css/hermes.css`; token passes between pages via sessionStorage (`ssh_session`/`ssh_token`) because both pages strip `?s=&t=` from the URL with replaceState. Memory/context files (SOUL.md, MEMORY.md, USER.md, config.yaml under the user's `~/.hermes/`) are edited through the existing `/api/files/read|save`. One running job per web session (second send returns success=False); jobs are dropped on disconnect/shutdown. Session HISTORY is readable from the web: `/api/hermes/history` {session_id(web), sid} runs `hermes sessions export --session-id <sid> --format jsonl -` (`build_export_command`) and `parse_session_jsonl` defensively extracts user/assistant text records (format NOT actually line-delimited anymore — current hermes emits a SINGLE json object with a nested `messages` array; the parser recurses into any dict with `role`+`content`, and still tolerates the old line-per-record format; tool-call noise is skipped); the web page loads it when a session is clicked — terminal/tmux-created sessions share the same ~/.hermes store, so dialogs started in KiTTY are readable/continuable in the browser. Install/setup is done manually over SSH (`curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash`, then interactive `hermes model` / `hermes portal` in a real terminal) — there are deliberately NO install buttons in the desktop GUI.

## Gotchas

- Saved passwords are Fernet-encrypted; the key lives OUTSIDE the repo at `%APPDATA%\SSH-Connect\.encryption_key` (auto-migrated from an old in-project key). Deleting it makes all saved profiles unreadable — never "clean it up".
- Host-key logic is duplicated as independent copies in `src/hostkeys.py` and `web-desktop/backend/ssh_manager.py`, both writing `SshHostKeys/known_hosts` (warn on new key, reject changed). Change both together.
- Web interface auth: a server token auto-generates into gitignored `web-desktop/backend/.server_token` and gates `POST /api/connect`; all other `/api/*` need a per-session in-memory token sent ONLY in the `X-Auth-Token` header (never in query params — uvicorn logs URLs and would leak it to `server.log`). The GUI reads the token file and passes session creds to the localhost server itself — passwords never appear in browser URLs. The auth middleware also rejects any request whose `Host` isn't `127.0.0.1`/`localhost` (DNS-rebinding guard). uvicorn is always launched with `--no-access-log` (set both in `src/gui.py` and in the `__main__` block of `web-desktop/backend/main.py`).
- KiTTY launch in `KittyController.start_kitty_with_logging()` passes args as a list to `subprocess.Popen` (no `shell=True` — avoids cmd injection via username/hostname) and validates `username`/`hostname` with a strict regex. It then minimizes the window via `minimize_window()` (`ShowWindow SW_MINIMIZE`) — PostMessage typing (password, tmux commands) still works minimized. The `move_cursor` helper is likewise started via an arg list with `CREATE_NO_WINDOW`.
- The web interface has NO terminal widget: its "Программы" menu lists installed utilities and sends a command to the already-open KiTTY window via `web-desktop/backend/kitty_launcher.py` (`PostMessage` WM_CHAR, class-name "KiTTY"), mirroring `KittyController` in `src/gui.py`. Commands always need a live KiTTY window. `POST /api/kitty/log` (incremental offset, `tail`, `reset`) mirrors the `%TEMP%\kitty_session.log` file.
- Clipboard sync with the docker browser (embedded in GUI button «Docker-браузер» — it opens `https://<host>:3001` AND auto-starts sync; no separate toggle button): `src/clipboard_sync.py` polls the Windows clipboard (Win32 via ctypes) and the container clipboard through the existing SSH connection using `docker exec <container> ... wl-paste`/`wl-copy` (the linuxserver/chrome container runs Wayland/labwc, NOT X11 — xclip won't work; needs `XDG_RUNTIME_DIR=/config/.XDG WAYLAND_DISPLAY=wayland-1` (IMPORTANT: it's `wayland-1`, NOT `wayland-0` — labwc exports `WAYLAND_DISPLAY=wayland-1` in `/defaults/startwm_wayland.sh`; the `wayland-0` socket in the container exists but has no browser attached, writing there makes the browser never see the text and breaks sync — do not "fix" it back to `wayland-0`)). Text is passed to the container base64-encoded through stdin (`echo ... | base64 -d | docker exec -i ... wl-copy`) to avoid command injection. Container name defaults to `chrome`, override with env `SSH_CONNECT_CLIPBOARD_CONTAINER`. The `_last_local`/`_last_remote` markers prevent echo loops. Sync runs once per docker-browser click; the thread is stopped on disconnect and window close (`_stop_clipboard_sync` in `src/gui.py`).
- Repo currently tracks only `.gitignore`, `LICENSE`, `README.md`; everything else is untracked, so no history to diff against — stage files explicitly. Runtime data (`ssh_connections.json`, `last_profile.txt`, `SshHostKeys/`, `Sessions/`, `Downloads/`, `.server_token`, `server.log`) is gitignored; the venv `SSH_env/` is self-ignored via its own inner `.gitignore` that contains `*`. `kitty.exe`/`kitty.ini`, `main.py`, `src/`, `web-desktop/`, `favicon.ico` etc. are NOT gitignored — never commit or delete runtime dirs, and don't expect `git status` to prove a file is safe to delete.
- Root `requirements.txt` is now pinned; `web-desktop/backend/requirements.txt` pins versions (fastapi==0.115.0, uvicorn==0.30.0, paramiko==5.0.0). `python-xlib` in the root list is a Linux-only dep — harmless but unused on Windows.
- `web-desktop/backend/main.py` locates the frontend via `_resource_path()` to support PyInstaller `_MEIPASS`; keep the relative-path fallbacks intact if you move files.
- Web frontend (`web-desktop/frontend/`) is a single vanilla-JS page (no build step, no CDN dependencies).
- Hermes pacer-proxy (free-provider rate limit, Gemini 60 RPM): `web-desktop/backend/hermes_pacer.py` deploys a stdlib-only transparent reverse-proxy (`~/.hermes/pacer_proxy.py`, running via nohup on `127.0.0.1:17901`) and flips `hermes config set model.base_url http://127.0.0.1:17901` so agent requests go THROUGH it. The proxy paces with a sliding 60-req/60s window (`PACER_RPM`) and forwards transparently to the original provider host saved in `~/.hermes/pacer.conf` (`upstream=https://...`) — no 429 storm on complex tasks. `build_pacer_ensure_command()` is idempotent (checks `/_health`, restarts only if dead), switches base_url ONLY after the proxy is confirmed alive (otherwise request still goes direct), and echoes `PACER_UPSTREAM/PACER_PORT/PACER_RUNNING/PACER_CFG` parsed by `parse_pacer_state`. It runs best-effort inside `POST /api/hermes/send` BEFORE each job (`pacer` key in the response) and on demand via `POST /api/hermes/pacer`. The web chat toolbar (`hermes.html`) shows a live pacer indicator `#pacer-ind` (clickable ⚪/🟢/🔴 dot, tooltip with port/base_url/upstream, 45s poll + refresh after each send). Port 17901 must not collide with reverse-access 17850. Rollback: `hermes config set model.base_url <старое>`, rm `~/.hermes/pacer.conf`. No pip deps, PyInstaller-safe.
